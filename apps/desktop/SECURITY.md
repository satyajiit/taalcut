# Desktop security (P1-B1, P1-B3, P1-B4)

How `apps/desktop` hardens Electron, item by item against [Electron's security checklist](https://www.electronjs.org/docs/latest/tutorial/security), and which test proves each item. "app" tests are `e2e/app.e2e.ts` (unpackaged build, Playwright for Electron); "packaged" tests are `e2e/packaged*.e2e.ts` (the ad-hoc signed `.app`, release and test builds); unit tests are in `test/`.

Run them: `pnpm --filter @taalcut/desktop test`, `… e2e`, `… e2e:packaged`, `… e2e:update`.

## Flag guard and build flavours

Fuses turn off `ELECTRON_RUN_AS_NODE`, `NODE_OPTIONS` and `--inspect`, but most Chromium switches have no fuse. Anyone who can pass switches already runs as the user. What the guard stops is them using Taalcut's signature, keychain items and privacy (TCC) permissions for code or behaviour Taalcut doesn't ship. The rules live in `src/main/security/switches.ts`. The bundle comes in two flavours, fixed at build time (`TAALCUT_BUILD_FLAVOUR`, baked in as `__TAALCUT_FLAVOUR__`; `packaging/build-settings.ts`):

- **release** (the default; everything users get). The first statement of `src/main/index.ts` reads `process.argv` (`--name`, `--name=value` and `-name`, up to a bare `--`). If any refused switch is present it removes them, prints why, for example "Taalcut: refusing to start with --no-sandbox (turns off a process sandbox). Release builds don't accept switches that weaken their security.", and calls `app.exit(1)`. Main's entry runs before Chromium starts its DevTools server or launches any child process, so none of it happens (checked on Electron 44).
- **test** (`e2e`, `e2e:packaged`). Accepts remote debugging and `--use-mock-keychain`, which every e2e launch passes (packaged and unpackaged: the vault then never touches the login keychain of whoever runs them), and refuses everything else in the table. Adds the test-only `--taalcut-self-test` and `--taalcut-update-feed` (`src/main/test-hooks.ts`). That code sits behind `__TAALCUT_FLAVOUR__ === 'test'` and is loaded with `import()`, so release bundles don't contain it. Test builds go to `release/test/`, are never notarised and are never distributed.

## sqlite-vec

`sqlite-vec` 0.1.9 is the only production dependency, and the only thing outside the bundles. Its native extension (`node_modules/sqlite-vec-darwin-arm64/vec0.dylib`) is unpacked from the ASAR (`asarUnpack`), because a library can't be loaded from inside the archive. `src/main/native/sqlite-vec.ts` resolves it through `@taalcut/library`'s `sqliteVecPath()`, which rewrites `app.asar` to `app.asar.unpacked`. Unpacked files are outside the ASAR integrity hash, but the dylib is covered by the app's code signature: electron-builder signs it with the app's identity and hardened runtime (`adhoc,runtime` locally).

**Entitlements: none extra.** In the packaged ad-hoc hardened app, `vec0.dylib` loads and answers a kNN query with the existing entitlements (packaged test "sqlite-vec loads from app.asar.unpacked and answers a kNN query"). Ad-hoc builds already carry `disable-library-validation`. Developer ID builds don't, and don't need it: library validation accepts a library signed by the same team, and electron-builder signs `vec0.dylib` with the app's Developer ID. Checked on 2026-10-12: in the Developer ID build, `vec0.dylib` is signed by team WW382UC8JD with hardened runtime and a timestamp, and the kNN self-test passes.

## GPU (ADR 0002)

Hardware acceleration is always on: nothing calls `app.disableHardwareAcceleration()` or appends a GPU switch, and **the app relies on no GPU-related switch**. It runs on Chromium's defaults, which on Apple silicon with Electron 44 put the UI on the GPU: GPU compositing and rasterisation (Skia Graphite on Metal), WebGL through ANGLE on Metal, WebGPU, accelerated 2D canvas and hardware video decode. The GPU runs in Chromium's own GPU helper process with the app's inherited entitlements; Metal needs no extra entitlement.

Never add: `--disable-gpu*`, `--use-gl`/`--use-angle=swiftshader` (software rendering), `--ignore-gpu-blocklist` (the blocklist steers around driver bugs), `--in-process-gpu` or `--disable-gpu-sandbox` (they weaken process isolation). A user who passes `--disable-gpu` (for example to get round a broken driver) is not stopped, but the CPU route is logged with its reason, as ADR 0002 requires: `[gpu] CPU fallback [{"feature":"gpu_compositing","status":"disabled_software","reason":"disabled on the command line: --disable-gpu"}, …]`.

Shown by: packaged "the UI runs on the GPU" (test build, `--taalcut-self-test=gpu`: hardware acceleration on, `gpu_compositing` and `rasterization` enabled, an active GPU; on a CI machine without a GPU, `CI` set, it accepts CPU fallbacks only if each has a reason and records them as annotations); "the release bundle keeps hardware acceleration on" (no `disableHardwareAcceleration(` or GPU `appendSwitch` in the release `index.mjs`); unit: `gpu.test.ts`, including a scan of `src/` for both.

## Updates (P1-B4)

A skeleton, not user-facing: `electron-updater` 6.8.9 with the `generic` provider checks 10 s after start and every 6 h, downloads automatically and installs on quit. Every event (`checking`, `available`, `not-available`, `progress`, `downloaded`, `staged`, `error`) is logged to stderr as `[update] {json}` and given to a listener (`src/main/update/`).

- **Feed.** Baked in at build time from `TAALCUT_UPDATE_FEED_URL`, `https` only (`packaging/build-settings.ts`). A build without a feed doesn't contain the updater at all; unpackaged runs never update. Only test builds may point elsewhere (`--taalcut-update-feed=<url>`, `https` or loopback `http`).
- **Checks.** Before every check, main fetches the channel file (at most 256 KiB) and its `.sig` (at most 2 KiB; `src/main/update/manifest-check.ts`) and verifies the Ed25519 envelope against the public key baked at build time (`TAALCUT_UPDATE_PUBLIC_KEY`): signature, channel, the file's sha256, expiry (90 days), and that it is no older than the newest signature this install accepted (`<userData>/updates/manifest-seen.json`). Only then does electron-updater check; its offer must carry exactly the signed version and zip sha512 (`isUpdateSupported`, before any download), and the downloaded zip must hash to the signed sha512 (`manifest-gate.ts`). Refusals are `rejected` with `desktop.update_manifest_untrusted|stale|mismatch|missing|unreadable`. A build without the key has no updater; a release build with a feed and no key, or with the e2e test key, fails to build (security review SB-19; signing and re-signing: `scripts/rollout/`). **Anti-rollback** (`src/main/update/candidate.ts`, `verify-download.ts`) then copies the downloaded zip into a private snapshot (`snapshot.ts`: a new 0700 folder, the file 0600 and fsynced, sha512 taken as it is written), unpacks the snapshot into a scratch folder and checks:
  - the zip holds `Taalcut.app` and nothing else; any other name is `desktop.update_untrusted_signer` (a name can carry newlines, and codesign prints paths raw);
  - `codesign --verify --deep --strict` passes (else `desktop.update_unreadable`);
  - the bundle's own `CFBundleShortVersionString` is strictly newer than the running app (`desktop.update_not_newer`), and codesign reports exactly one TeamIdentifier, the running app's (`desktop.update_untrusted_signer`; two such lines mean a path added one, and are unreadable);
  - the signature satisfies `anchor apple generic and identifier "<running app's>" and certificate leaf[subject.OU] = "<running team>"` (`codesign -R`), so trust never rests on codesign's text output (`desktop.update_untrusted_signer`);
  - the snapshot still has the sha512 it was written with (`desktop.update_changed`).

  A refusal is a typed error in an `UpdateEvent` `{ type: "rejected", error }`, logged as `[update] {json}`, and the zip never reaches Squirrel: electron-updater's `autoInstallOnAppQuit` is off. After `verified`, main points Squirrel at its own loopback feed (`squirrel-feed.ts`, random-token URLs) that serves the snapshot, not electron-updater's cache file, which any process of the user could rewrite during verification. The feed holds back the last chunk unless every byte still matches the verified sha512, so a changed snapshot gives Squirrel a short, failed download. Feed and snapshot are removed once Squirrel has staged the update or failed. Last, Squirrel.Mac (Electron's native updater) accepts the new bundle only if its code signature satisfies the running app's designated requirement.
- **Ad-hoc builds can't update.** An ad-hoc app has no team ID, so anti-rollback refuses every update (`desktop.update_untrusted_signer`, team `none`) before Squirrel sees it. Squirrel would refuse it too: an ad-hoc designated requirement is the app's own cdhash.
- **Developer ID builds update.** With `TAALCUT_MAC_IDENTITY="Developer ID Application: Matterward Labs Private Limited (WW382UC8JD)" pnpm --filter @taalcut/desktop e2e:update` (or `e2e:packaged`), nothing is published or notarised. On 2026-10-12 the same test saw `checking → available → progress → downloaded → verified → staged`. It then quit the app; ShipIt swapped the bundle in place, the clone's `Info.plist` read 0.0.1, and the installed bundle passed `codesign --verify --deep --strict`. Squirrel's swap needs no notarisation, only a matching designated requirement; users still need a notarised N for Gatekeeper's first launch.
- **Hostile feeds are refused** (`packaged-update.e2e.ts`, ad-hoc and Developer ID, 2026-10-12). A feed that labels N itself as 0.0.2, with a correct sha512, gives `rejected` `desktop.update_not_newer` (0.0.0 vs 0.0.0). N+1 re-signed by someone else (ad-hoc) gives `rejected` `desktop.update_untrusted_signer`. Neither is staged, and the app stays at 0.0.0 after quitting. Channel files are refused before any zip is requested when signed with another key (`desktop.update_manifest_untrusted`), changed after signing (`mismatch`) or unsigned (`missing`) (same file, Developer ID, 2026-10-15).

## CSP

```
default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' data: blob:; media-src 'self' blob:;
font-src 'self'; connect-src 'self'; worker-src 'self'; frame-src 'none'; manifest-src 'none';
object-src 'none'; base-uri 'none'; frame-ancestors 'none'; form-action 'none'
```

The agreed baseline, tightened: `frame-src 'none'` (the app frames nothing), `manifest-src 'none'`, and `worker-src 'self'` stated outright. It is sent on every `app://` response, not only HTML, because workers take their CSP from their own script's response. Other headers: `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, `Cross-Origin-Opener-Policy: same-origin`, `Cross-Origin-Resource-Policy: same-origin`.

**Loosened only in development:** pages from the Vite dev server get `'unsafe-inline'` for scripts (React refresh preamble) and styles (Vite injects `<style>`), and `ws://localhost:<port>` for HMR. Never in a packaged build.

**For the renderer:** no inline `<script>`, no `eval`/`new Function`, no `<style>` elements or `style="…"` attributes set as HTML (setting `element.style.x` from JavaScript is fine). Libraries that inject `<style>` at run time need their CSS imported as a file instead.

## Fuses

Flipped by electron-builder before signing (`packaging/fuses.ts`, one source of truth for the build and the test).

| Fuse | Value | Why |
| --- | --- | --- |
| RunAsNode | off | `ELECTRON_RUN_AS_NODE` would turn the signed app into a general-purpose Node. Utility processes don't need it |
| EnableCookieEncryption | on | Cookies on disk are encrypted with a keychain key |
| EnableNodeOptionsEnvironmentVariable | off | `NODE_OPTIONS=--require …` would inject code into main |
| EnableNodeCliInspectArguments | off | `--inspect` would open a debugger on main |
| EnableEmbeddedAsarIntegrityValidation | on | `app.asar` must match the hash in `Info.plist`, which the code signature seals |
| OnlyLoadAppFromAsar | on | No loose `app/` folder can replace the archive |
| LoadBrowserProcessSpecificV8Snapshot | off | No custom snapshot ships |
| GrantFileProtocolExtraPrivileges | off | `file://` gets no special powers; the app uses `app://` |
| WasmTrapHandlers | on (Electron default) | Not exposed by electron-builder; V8's guard-page bounds checks |

Behavioural proof on the packaged app (`packaged-hardening.e2e.ts`): `ELECTRON_RUN_AS_NODE=1` still starts the app and never runs the script; `NODE_OPTIONS=--require` and `--inspect` do nothing; a copy of the app with one byte changed in `app.asar` dies with "Integrity check failed".

## Signing, entitlements and notarisation (P1-B3)

Hardened runtime is on for every binary. **Identity**: `TAALCUT_MAC_IDENTITY`, the full certificate name. It defaults to **ad-hoc** (`-`) for CI and contributors. Release builds use `TAALCUT_MAC_IDENTITY="Developer ID Application: Matterward Labs Private Limited (WW382UC8JD)"` from the login keychain (the PO's decision, 2026-10-12). electron-builder gets the name without "Developer ID Application:" because it refuses that prefix. Our own `codesign` calls keep the full name, because the bare name also matches the team's "Apple Distribution" certificate. electron-builder looks for a keychain identity whose name contains "-" before falling back to ad-hoc, so an ad-hoc build refuses to run when one exists, or when `CSC_LINK`/`CSC_NAME` are set. A Developer ID build sets `forceCodeSigning`: if the named identity isn't in the keychain, the build fails. Without it, electron-builder would log the problem and ship the app unsigned.

What gets signed, inside-out (`packaging/builder-config.ts`):

Not requested: `allow-unsigned-executable-memory` (not needed by current Electron), any other `device.*` entitlement (no camera), or other `personal-information.*` entitlements.

**The mac helper's pin** (`packaging/mac-helper.ts`). Swift 6.3.3 doesn't compile the helper to the same bytes twice, so no pin is committed: every package makes its own. `package` (and `package:dir`, `scripts/package-e2e.mjs`) runs `native/mac-helper/build.sh`, and the desktop build bakes the helper's signature-free sha256 (the bytes before the code signature, with the sizes signing rewrites zeroed, so re-signing keeps it) into the bundles as `__TAALCUT_MAC_HELPER_PIN__`. The pin is code in `app.asar`, which ASAR integrity covers, not a file beside the helper that could be replaced with it. afterPack refuses to finish a package whose bundles carry no pin, that has no helper, or whose packed helper is another build. At run time a packaged app's utility processes start the helper only while its digest is that pin (`roots/mac-helper-resolver.ts`; `media.sidecar_pin_mismatch` otherwise, also when the bundle has no pin), so a helper replaced inside an installed app is refused before it runs (`e2e/packaged-test-build.e2e.ts`). A development run's helper (`native/mac-helper/dist` or `TAALCUT_MAC_HELPER`) is unpinned.

**Notarisation** (`packaging/notarize.ts`). It uses an App Store Connect API key that the owner stores once in the login keychain: `xcrun notarytool store-credentials taalcut-notary --key AuthKey_<id>.p8 --key-id <id> --issuer <issuer>`. The build only ever names the profile (`TAALCUT_NOTARY_PROFILE`, default `taalcut-notary`). In `afterSign` the app is zipped with `ditto`, submitted with `xcrun notarytool submit … --keychain-profile taalcut-notary --wait`, and stapled with `xcrun stapler staple`; the zip and DMG are then made from the stapled app. The signed DMG is submitted and stapled the same way. A rejected submission fails the build and prints Apple's log (`notarytool log`). It runs only for Developer ID **release** builds whose profile exists (`notarytool history --keychain-profile …` succeeds; its output is discarded). It never runs for test builds or with `TAALCUT_NOTARIZE=0` (set by `scripts/package-e2e.mjs`). Otherwise the build prints why it skipped, for example `notarisation skipped: keychain profile "taalcut-notary" not found. Store it once with: …`. With `TAALCUT_NOTARIZE=1` every skip is an error instead. `TAALCUT_NOTARY_KEYCHAIN` names a keychain file other than the default, and is passed to every `notarytool` call as `--keychain`.

**CI release** (`.github/workflows/release.yml`, manual only). The certificate and the API key come from the `release` environment's secrets (required reviewer: the PO; deployment branch `main` only), so no other branch's code is signed or notarised, and `publish-release.yml` publishes only a Release run built from `main` (security review SB-41; moving the secrets there is the owner's step in the repository settings). They go into a temporary keychain with a random password, together with Apple's Developer ID G2 intermediate, which is pinned by SHA-256. The `.p12` and `.p8` files are deleted straight after import. The notary profile `taalcut-ci-notary` lives in that keychain. electron-builder searches only that keychain (`CSC_KEYCHAIN`), and `TAALCUT_NOTARIZE=1` is set. An `always()` step deletes the keychain and the key directory. The FFmpeg sidecars are signed only after a hash gate passes: every file must be byte-identical to the committed `tools/ffmpeg/dist/BUILDINFO.json`, with no extra files (`scripts/check-ffmpeg-dist.mjs`). The gate also runs on a restored cache entry, so the Actions cache can't swap the binaries. The mac helper is built in the same job by `package` (`native/mac-helper/build.sh`, signed from the temporary keychain) and pinned by that package, so no cached or committed helper is shipped. The DMG is uploaded as a workflow artefact and never published.

**Verification**: `pnpm --filter @taalcut/desktop verify:signature`, also the last step of `package` and `package:dir`. Without paths it checks what the last package made, in the output directory of the flavour `out/build-info.json` records (`release/`, `release/test/`, or `TAALCUT_PACKAGE_OUTPUT`; `packaging/build-output.ts`, the same function that tells electron-builder where to write): the app and that directory's DMGs, or with `--built-app` (`package:dir`) the app alone. For the app it runs `codesign --verify --deep --strict` and checks every Mach-O inside (`--deep` skips binaries in `Resources/`) for a valid signature, hardened runtime, the app's team and a secure timestamp. It then runs `spctl -a -vv -t exec` and `stapler validate`. For the DMG: `codesign --verify --strict`, `spctl -a -t open --context context:primary-signature`, `stapler validate`. Gatekeeper rejects a Developer ID build until it is notarised, so that verdict fails the script only with `--notarized`. With `--notarized`, the script also requires `source=Notarized Developer ID` (not just `accepted`) and a stapled ticket.

Results for the Developer ID release package, 2026-10-12:

- **App:** `codesign --verify --deep --strict` reports "valid on disk" and "satisfies its Designated Requirement". The chain is Developer ID Application: Matterward Labs Private Limited (WW382UC8JD) < Developer ID Certification Authority < Apple Root CA, timestamped. All 17 Mach-O files inside (14 for Electron and sqlite-vec, plus ffmpeg, ffprobe and libMoltenVK) are signed by WW382UC8JD with hardened runtime and a timestamp. Entitlements: `allow-jit` only.
- **DMG:** signed by the same identity and timestamped.

## Known gaps

- **Update integrity (P1-B5): both parts done, edges open.** Anti-rollback and signed channel files (SB-19) are in place; see [Updates](#updates-p1-b4). Still open: a build-time minimum supported version; a feed that keeps serving refused updates, or withholds a fresh signature, wastes downloads or stops updates but installs nothing; and key operations. A signature not renewed within 90 days stops every install updating (`desktop.update_manifest_stale`) until `release.mjs resign` runs. Rotating the key strands installs that haven't yet taken a build that bakes the new public key (docs/release.md, "Signed channel files").
- **Logging switches truncate their file before main runs.** Electron opens the file named by `--enable-logging=file --log-file=<path>` (or `ELECTRON_ENABLE_LOGGING=file` with `ELECTRON_LOG_FILE`) in C++, before the entry script. It **truncates an existing file** at that path, checked on Electron 44 (2026-10-12). The flag guard then exits before anything is logged, so the file ends up empty. Anyone who can launch Taalcut with arguments could use this to truncate a file Taalcut may write but they may not (a TCC-protected folder the user granted Taalcut). No fuse covers it. Raise it upstream (a fuse for the logging switches); until then, the guard limits it to that one truncation.
- **Notarisation hasn't run yet.** The `taalcut-notary` profile isn't in the keychain (`notarytool`: "No Keychain password item found for profile: taalcut-notary"), so nothing has been submitted to Apple. Developer ID builds are signed and verified, and Gatekeeper reports "Unnotarized Developer ID" until then. The release workflow is ready but hasn't run, and its secrets aren't set yet.
- **Ad-hoc builds have no FFmpeg Vulkan path.** Without a team, dyld won't let ffmpeg load libMoltenVK under the hardened runtime, and the sidecars get no `disable-library-validation` (decision 2026-10-12). CI and contributor builds therefore run libplacebo and the Vulkan filters on the CPU fallback. Media's backend selection must record that reason (ADR 0002); VideoToolbox is unaffected.
- **`webContents.getLastWebPreferences()` is undocumented** (absent from Electron's typings). The launch test uses it as the brief asks. If an upgrade removes it, fall back to the unit test of `secureWebPreferences` plus the behavioural checks.
- **No Trusted Types or COEP yet.** `require-trusted-types-for 'script'` and `Cross-Origin-Embedder-Policy` would tighten further but may break renderer libraries. The renderer sets no HTML from strings (no `innerHTML`, `dangerouslySetInnerHTML` or `eval`), so Trusted Types may already hold: the next step is a report-only header in development and test builds, with the renderer e2e failing on a report (core request `trusted-types-report-only`, security review SB-9).
